# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### DocumentConverter.Web (dotnet run / dotnet DocumentConverter.Web.dll)

**Description**: Startup interface of the ASP.NET Core web host, which is the single composition root of the product — nothing in Application, Infrastructure or Security is reachable unless it is registered by Program.cs. There are no positional CLI arguments or option switches in the delivered source: the host is configured through the standard ASP.NET Core configuration providers (appsettings.json, user secrets, environment variables, and host command-line arguments in the default order), so the effective startup interface is the configuration key set consumed at boot plus the framework-provided host switches. Services wired here include the AppDbContext for PostgreSQL, EF-backed health checks, OTLP telemetry exporters, endpoint routing, SignalR hubs, middleware, hosted services and the Blazor component tree.

**Source File**: `src/DocumentConverter.Web/Program.cs, src/DocumentConverter.Web/appsettings.json, src/DocumentConverter.Infrastructure/Persistence/DatabaseExtensions.cs, src/DocumentConverter.Infrastructure/Security/StorageEncryption/StorageEncryptionOptions.cs`

**Options**:

- `ConnectionStrings:DefaultConnection`(string): required - Primary database connection string consumed by AddConfiguredDbContext, which reads it to select the EF Core provider (PostgreSQL via Npgsql or SQL Server). The shipped appsettings.json pins a SQL Server endpoint (localhost:1433, user sa, TrustServerCertificate=True, MARS enabled) with an inline plaintext password, while the Web csproj pulls Npgsql — a provider/connection mismatch that must be resolved per deployment. (default: `Server=localhost,1433;User Id=sa;Password=<inline plaintext>;TrustServerCertificate=True;MultipleActiveResultSets=True`)
- `Storage:RootPath`(string): optional - Filesystem root used by the storage subsystem when the local provider is active. Points at the application-private data directory in the shipped configuration. (default: `./app_data/storage`)
- `Storage:Encryption:Enabled`(boolean): optional - Gates the AES-256-GCM envelope encryption behaviour of the storage layer. Bound from the 'Storage:Encryption' section by StorageEncryptionOptions. When false, documents are written without the per-document ephemeral DEK wrap.
- `Storage:Encryption:MasterKeyEncryptionKey`(string (Base64, 32 bytes decoded)): required - Base64-encoded 256-bit Master Key Encryption Key (KEK) used to wrap per-document ephemeral data encryption keys. Documented in the options class as production-supplied via environment variable or an external secret store rather than checked-in configuration — this key is the root of trust for all encrypted documents at rest.
- `ClamAV:Enabled`(boolean): optional - Controls whether uploaded attachments are scanned by the ClamAV integration. Shipped disabled, meaning the virus-scanning control is off by default in this configuration shape. (default: `false`)
- `Logging:LogLevel:Default`(string (Trace|Debug|Information|Warning|Error|Critical|None)): optional - Global minimum log level for the host. (default: `Information`)
- `Logging:LogLevel:Microsoft.EntityFrameworkCore`(string): optional - EF Core category log level. Set to Information in the shipped configuration, which raises log verbosity for query text — operationally useful but a data-exposure consideration because parameter values may appear in logs. (default: `Information`)
- `AllowedHosts`(string (semicolon-separated host list or '*')): optional - ASP.NET Core host filtering setting. Shipped as '*' (wildcard), which disables host-header allowlist enforcement — relevant to host-header injection and password-reset poisoning classes of attack at the reverse proxy tier. (default: `*`)
- `--urls / ASPNETCORE_URLS`(string (semicolon-separated URLs)): optional - Standard ASP.NET Core Kestrel binding switch supplied by the framework host, not declared in the source tree. Determines the listening endpoints for the web host and therefore the network surface at which every HTTP boundary above becomes reachable. (default: `http://localhost:5000;https://localhost:5001`)
- `ASPNETCORE_ENVIRONMENT`(string (Development|Staging|Production)): optional - Selects the hosting environment. This value is functionally load-bearing: InitializeDatabaseAsync applies pending EF Core migrations only when the host is running in Development, so the switch determines whether schema migration is automatic or an explicit deployment step. (default: `Production`)
- `OTEL_EXPORTER_OTLP_ENDPOINT`(string (URL)): optional - OTLP exporter target for the OpenTelemetry tracing and metrics pipeline configured at startup. Traces and metrics cover the conversion pipeline, RAG retrieval stages and general request flow.

**Usage Examples**:

```bash
dotnet run --project src/DocumentConverter.Web/DocumentConverter.Web.csproj
```

```bash
ASPNETCORE_ENVIRONMENT=Development ConnectionStrings__DefaultConnection='Host=localhost;Database=econverter;Username=postgres;Password=***' dotnet DocumentConverter.Web.dll --urls http://0.0.0.0:8080
```

```bash
Storage__Encryption__Enabled=true Storage__Encryption__MasterKeyEncryptionKey='<base64-256-bit-KEK>' dotnet DocumentConverter.Web.dll
```

### DocumentWorker (dotnet run / dotnet DocumentWorker.dll)

**Description**: Startup interface of the standalone background worker host, which bootstraps the .NET Generic Host (configuration sources, logging, DI) and runs the Worker background service plus ConsoleJobNotificationService. It consumes the queue and executes the conversion job lifecycle with streamed storage I/O, so it must be pointed at the same database, storage root and encryption key material as the web host. Like the web host it exposes no custom positional arguments in the delivered source; the startup interface is the .NET host configuration provider set. ConsoleJobNotificationService implements the job notification contract by writing structured progress, completion, failure, cancellation and batch-update messages to the console — effectively making stdout the worker's operational output channel.

**Source File**: `src/Workers/DocumentWorker/Program.cs, src/Workers/DocumentWorker/DocumentWorker.csproj, src/DocumentConverter.Infrastructure/Ocr/TesseractOcrEngine.cs`

**Options**:

- `ConnectionStrings:DefaultConnection`(string): required - Database connection string for the worker's DbContext registrations. Must resolve to the same database as the web host because SQL is the authoritative source of ProcessingJob state; the broker only handles delivery. The worker csproj references SQL Server, PostgreSQL and InMemory providers.
- `RabbitMQ connection settings`(string (host/port/credentials)): optional - Broker endpoint and credentials backing the messaging registration. JobMessage envelopes are published by the web host and consumed here; a NoOpQueuePublisher fallback exists so environments without a broker can still run, in which case the worker's database polling path carries the work.
- `Storage:RootPath`(string): required - Storage root shared with the web host. The worker performs the actual document read/write stream I/O during conversion, including streamed hashing. (default: `./app_data/storage`)
- `Storage:Encryption:Enabled / Storage:Encryption:MasterKeyEncryptionKey`(boolean / string (Base64)): required - Encryption gate and KEK material. The worker must hold the same KEK as the web host, otherwise documents written by one host cannot be read and processed by the other — this is the tightest cross-host coupling in the deployment.
- `Tessdata path (OS-level resolution)`(string (filesystem path)): required - The TesseractOcrEngine resolves and symlinks the native libtesseract/leptonica libraries cross-platform through a DllImportResolver and constructs a TesseractEngine from a tessdata directory. The language-pack location is an OS-level dependency rather than an application setting, and is the most frequent source of worker deployment failure.
- `DOTNET_ENVIRONMENT`(string (Development|Staging|Production)): optional - Standard Generic Host environment selector controlling which configuration sources and environment-specific overrides apply to the worker. (default: `Production`)

**Usage Examples**:

```bash
dotnet run --project src/Workers/DocumentWorker/DocumentWorker.csproj
```

```bash
ConnectionStrings__DefaultConnection='Host=db;Database=econverter;Username=postgres;Password=***' Storage__Encryption__MasterKeyEncryptionKey='<base64-256-bit-KEK>' dotnet DocumentWorker.dll
```

## API Interfaces

### POST /api/documents/upload

**Description**: Presigned-style document ingestion route registered by MapDocumentEndpoints. Accepts an uploaded document stream, persists the blob through the Storage application abstraction (streamed hashing during write), and creates the Document aggregate plus its first DocumentVersion. Returns the new document identifier and lifecycle status to the caller.

**Source File**: `src/DocumentConverter.Web/Endpoints/DocumentEndpoints.cs :: MapDocumentEndpoints`

**Request Format**: multipart/form-data (file stream plus optional folderId part)

**Response Format**: application/json (document id, name, storage key, processing status)

**Authentication**: ASP.NET Core Identity cookie (the /api/documents group is mounted behind RequireAuthorization)

### GET /api/documents

**Description**: Lists the documents visible to the authenticated principal. The result set is scoped per owner at the aggregate level, so the identity resolved from the cookie determines which rows are returned. Backed by IApplication DocumentService.

**Source File**: `src/DocumentConverter.Web/Endpoints/DocumentEndpoints.cs :: MapDocumentEndpoints`

**Request Format**: query string (folder scoping / paging parameters)

**Response Format**: application/json (array of document DTOs)

**Authentication**: ASP.NET Core Identity cookie (RequireAuthorization)

## Integration Suggestions

### Asynchronous job submission and status polling over the /api/processing surface

The /api/processing group is the only endpoint surface that uses a named authorization policy ('RequireUser') instead of the bare RequireAuthorization, making it the intended programmatic integration point for the Headless/API Consumer persona. Integrators should discover supported converter pairs from IConverterCatalogService before submitting work, then submit a job and consume terminal state either by polling the status route or by subscribing to the SignalR hub that the web host's JobProcessorWorker and JobNotificationService expose.

**Example Code**:

```
# 1) Discover supported converter pairs (IConverterCatalogService surface)
curl -s -b cookies.txt https://econverter.example.com/api/processing/converters

# 2) Submit a conversion job (RequireUser policy)
curl -s -b cookies.txt -X POST https://econverter.example.com/api/processing/jobs \
  -H 'Content-Type: application/json' \
  -d '{"documentId":"<guid>","sourceFormat":"docx","targetFormat":"pdf"}'
# -> {"jobId":"<guid>","status":"Queued"}

# 3) Poll job state
curl -s -b cookies.txt https://econverter.example.com/api/processing/jobs/<jobId>

# 4) Fetch the produced artifact once the job reaches a terminal state
curl -s -b cookies.txt -o out.pdf \
  https://econverter.example.com/api/processing/jobs/<jobId>/result
```

**Best Practices**:

- Authenticate first against /account/login with form-encoded credentials and persist the Identity cookie — every /api/* route is gated by RequireAuthorization, so an unauthenticated call returns 401 rather than a partial result.
- Observe the family/entity split between authorization patterns: /api/processing uses the named 'RequireUser' policy while documents, editor and intelligence use the default policy. Treat a 401/403 here as a policy misconfiguration signal, not a route typo.
- Prefer the queue-backed /api/processing path over the synchronous conversion route for anything long-running; the worker model exists specifically to decouple heavy conversions from the interactive request thread.
- Submit a batch job rather than a loop of single submissions when converting many documents — batch jobs carry their own completion detection and batch-update notifications.
- Never assume a job has finished from submission success alone; SQL is the authoritative job state and the broker only handles delivery, so poll the status route or subscribe to the hub.
- Treat the produced output artifact as an ephemeral handoff; the output document is recorded in the ProcessingJobOutput JSON-converted column and points back at the storage layer.

### Document ingestion and lifecycle automation over the /api/documents and /api/editor surfaces

The /api/documents group covers upload, listing, rename, move, delete, folder creation and rename, plus the AI intelligence routes; /api/editor serves the inline PDF stream and accepts edit operations. All routes are mounted behind RequireAuthorization and delegate to Application-layer services, so a client integration must carry a valid Identity session and must respect per-owner aggregate scoping — a document owned by another principal is not merely inaccessible but should be treated as non-existent.

**Example Code**:

```
# Upload
curl -s -b cookies.txt -X POST https://econverter.example.com/api/documents/upload \
  -F 'file=@contract.docx' -F 'folderId=<guid>'

# List (result set is scoped to the authenticated owner)
curl -s -b cookies.txt https://econverter.example.com/api/documents

# Rename — RenameDocumentRequest { NewName: string }
curl -s -b cookies.txt -X POST https://econverter.example.com/api/documents/<id>/rename \
  -H 'Content-Type: application/json' -d '{"newName":"Contract v2.docx"}'

# Move — MoveDocumentRequest { FolderId: Guid? }; null moves to root
curl -s -b cookies.txt -X POST https://econverter.example.com/api/documents/<id>/move \
  -H 'Content-Type: application/json' -d '{"folderId":null}'

# Folder creation — CreateFolderRequest { Name: string, ParentFolderId: Guid? }
curl -s -b cookies.txt -X POST https://econverter.example.com/api/documents/folders \
  -H 'Content-Type: application/json' -d '{"name":"2026 Contracts","parentFolderId":null}'

# Inline PDF preview for the editor
curl -s -b cookies.txt -o preview.pdf https://econverter.example.com/api/editor/<id>/pdf
```

**Best Practices**:

- Build the request bodies against the declared record shapes (RenameDocumentRequest, MoveDocumentRequest, CreateFolderRequest, RenameFolderRequest) — the minimal API model binder is strict about these DTOs.
- Distinguish 404 from 403 when probing identifiers. The correct security posture is to return not-found for resources the caller does not own; a 403 that confirms existence is itself an enumeration oracle.
- Reuse the folder hierarchy in /api/documents/folders rather than encoding paths in names — folder relationships are first-class rows backed by the Folder EF configuration.
- Drive preview and editing through /api/editor rather than downloading raw files, so the server-side PdfEngine applies page-structure and redaction operations consistently.
- Validate returnUrl-shaped inputs on any client that constructs redirects; the server-side UrlIsValid guard only accepts safe local relative paths, so absolute or protocol-relative URLs will be rejected.

### Outbound LLM provider integration through IExternalAiClient

The AI stack reaches OpenAI, Anthropic Claude and Google Gemini through a single provider-abstracting client that normalises three divergent streaming dialects into one contract. Implementers and operators should treat external providers as an optional, explicitly routed outbound integration: the retrieval core (HNSW vector index, BM25 lexical index, RRF fusion, MMR diversification, LLM reranking) is engineered to run in-process against locally held indexes, so a deployment can operate on-premise without any outbound LLM call.

**Example Code**:

```
// Implement the outbound boundary and keep reasoning tokens separate from visible text.
public sealed class MyExternalAiClient : IExternalAiClient
{
    public async IAsyncEnumerable<ExternalAiStreamChunk> SynthesizeAnswerAsync(
        string prompt,
        [EnumeratorCancellation] CancellationToken cancellationToken)
    {
        await foreach (var raw in StreamFromProviderAsync(prompt, cancellationToken))
        {
            // Provider-native reasoning deltas stay on ReasoningDelta so callers can
            // render or discard thinking output independently of the answer text.
            yield return new ExternalAiStreamChunk(
                ReasoningDelta: raw.IsReasoning ? raw.Text : null,
                ContentDelta:   raw.IsReasoning ? null : raw.Text);
        }
    }
}
```

**Best Practices**:

- Honour the two-channel chunk contract: never fold ReasoningDelta into ContentDelta, because downstream consumers may discard thinking output for compliance or rendering reasons.
- Tolerate providers that emit only one of the two channels — both deltas are nullable by design, which keeps the streaming contract allocation-cheap across divergent dialects.
- Route provider selection through configuration rather than code so a regulated deployment can disable outbound calls entirely and rely on the local retrieval stack.
- Gate AI answers on the benchmark harness (RagBenchmarkRunner reports Recall, Precision, MRR, nDCG and faithfulness) before shipping a retrieval or prompt change — it exists as a quality gate, not a demo.
- Keep provider credentials in the secret store rather than configuration files, matching the pattern already documented for the storage KEK.

### Deployment coupling between the web host, the worker host and the shared cryptographic material

The web host and DocumentWorker are separate executables that must agree on four things to function as one system: the database connection string (SQL is authoritative job state), the storage root, the RabbitMQ broker (or the NoOpQueuePublisher fallback with database polling), and the encryption KEK. The IExternalAiClient and Tesseract native library are the two remaining environment-sensitive dependencies. Misconfiguration in any of these surfaces at startup rather than at the first request, which is why InitializeDatabaseAsync performs an explicit readiness probe before the host serves traffic.

**Example Code**:

```
# Docker-compose shape: both hosts share config and secret material.
services:
  web:
```

**Best Practices**:

- Provision the Storage:Encryption:MasterKeyEncryptionKey through an environment variable or external secret store — the options class explicitly documents that it must not be checked in. A mismatched KEK between web and worker silently breaks document processing.
- Resolve the PostgreSQL-versus-SQL-Server provider mismatch before deployment: appsettings.json ships a SQL Server (sa) connection string while the Web and Worker projects reference the Npgsql provider, and AddConfiguredDbContext branches on the connection string shape.
- Restrict AllowedHosts to the real deployment hostnames instead of the shipped wildcard '*', so host-header injection and password-reset poisoning cannot reach the application through a reverse proxy.
- Lower Logging:LogLevel:Microsoft.EntityFrameworkCore below Information in production; query-text logging at Information can surface parameter values in centralised log storage.
- Enable ClamAV scanning if uploads are accepted from untrusted principals; it is shipped disabled, so the control is absent by default.
- Run the worker as a scaled-out replica set pointed at the same broker and database — the queue-backed model exists precisely so conversion throughput can scale independently of the web front end.
- Pre-stage the native Tesseract/libtesseract/leptonica libraries and tessdata language packs in the worker image; the DllImportResolver is the most common cause of worker startup failure.
