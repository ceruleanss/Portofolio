# System Boundary Interface Documentation

This document describes the system's external invocation interfaces, including CLI commands, API endpoints, configuration parameters, and other boundary mechanisms.

## Command Line Interface (CLI)

### dotnet run --project src/CharityPlatform.Api

**Description**: Startup of the ASP.NET Core minimal-hosting-model backend API. Bootstraps the WebApplication host, registers DI for Application/Infrastructure/Persistence/Telemetry, configures JWT bearer authentication, OpenAPI/Swagger, Serilog, OpenTelemetry, and composes the HTTP middleware pipeline before app.Run(). Every HTTP request into the charity platform flows through this pipeline.

**Source File**: `src/CharityPlatform.Api/Program.cs`

**Options**:

- `ASPNETCORE_ENVIRONMENT`(string): optional - ASP.NET Core hosting environment; selects configuration sources and error verbosity. (default: `Development`)
- `ASPNETCORE_URLS`(string): optional - Kestrel binding URLs. Production compose sets http://+:8080 so the nginx edge proxy can reach the API container.
- `ConnectionStrings__DefaultConnection`(string): required - PostgreSQL/Supabase connection string consumed by EF Core via AddInfrastructure.
- `Supabase__Url`(string (URL)): required - Supabase managed platform base URL used for identity profile synchronization.
- `Supabase__ServiceKey`(string (secret)): required - Supabase service role key granting privileged access to the identity layer.
- `Supabase__JwtSecret`(string (secret)): required - JWT signing secret used by the JwtBearer token validation parameters (Microsoft.IdentityModel.Tokens).
- `PaymentGateways__ToyyibPay__SecretKey`(string (secret)): required - Malaysian payment gateway secret key for the ToyyibPayAdapter (FPX/local bank channels).

**Usage Examples**:

```bash
dotnet run --project src/CharityPlatform.Api
```

```bash
ASPNETCORE_ENVIRONMENT=Production ASPNETCORE_URLS=http://+:8080 dotnet CharityPlatform.Api.dll
```

### otelcol --config deploy/observability/otel-collector-config.yml

**Description**: Telemetry ingestion hub. Accepts OTLP from all esalam services on gRPC 4317 and HTTP 4318, applies batch (timeout 1s, send_batch_size 1024) and memory_limiter (check_interval 1s, limit 75%, spike 20%) processors, then fans out: metrics to a Prometheus exporter on 8889 (namespace esalam), spans to Tempo over OTLP/gRPC (tempo:4317, tls insecure), logs to Loki push API (http://loki:3100/loki/api/v1/push), plus a debug exporter.

**Source File**: `deploy/observability/otel-collector-config.yml`

**Options**:

- `receivers.otlp.protocols.grpc.endpoint`(string (host:port)): optional - OTLP gRPC receiver endpoint. (default: `0.0.0.0:4317`)
- `receivers.otlp.protocols.http.endpoint`(string (host:port)): optional - OTLP HTTP receiver endpoint. (default: `0.0.0.0:4318`)
- `exporters.prometheus.endpoint`(string (host:port)): optional - Prometheus exporter endpoint queried by the prometheus.yml otel-collector scrape job. (default: `0.0.0.0:8889`)
- `exporters.prometheus.namespace`(string): optional - Metric namespace prefix applied to all exported metrics. (default: `esalam`)
- `exporters.loki.endpoint`(string (URL)): optional - Loki HTTP push API endpoint for log export. (default: `http://loki:3100/loki/api/v1/push`)

**Usage Examples**:


## API Interfaces

### POST/GET /api/v1/Donations

**Description**: One-off donation creation and processing endpoints. Translates HTTP calls into CQRS commands/queries in Application.Donations. Highest business-value surface: money movement, tax receipt generation, and per-donor giving history exposure.

**Source File**: `src/CharityPlatform.Api/Controllers/Donations/DonationsController.cs`

**Request Format**: application/json (donation command/query DTOs from CharityPlatform.Contracts.Donations); tax receipt requests may carry file upload

**Response Format**: application/json (ApiResponse envelope; unwrapped Result<T> payload via HandleResult)

**Authentication**: JWT Bearer (ASP.NET Core [Authorize] attributes; token validated via JwtBearer in Infrastructure.DependencyInjection)

### GET/POST/PUT/DELETE /api/v1/campaigns

**Description**: Campaign lifecycle management: create, read, update, publish/close, category taxonomy, picture/video galleries, Qurban/Aqiqah/Waqf capacity tier configuration, and reviewer moderation actions. Uses ICommandHandler/IQueryHandler CQRS dispatch, keeping the API layer thin.

**Source File**: `src/CharityPlatform.Api/Controllers/Campaigns/CampaignsController.cs`

**Request Format**: application/json (CharityPlatform.Contracts.Campaigns request contracts) plus multipart/form-data for media upload (IFormFile)

**Response Format**: application/json (ApiResponse.Fail on validation/BadRequest; ApiResponse.Ok with DTO payload on success)

**Authentication**: JWT Bearer ([Authorize] attributes declared at controller/action level)

### GET/POST/PUT /api/v1/auth

**Description**: Primary trust boundary of the API surface. Merges Supabase identity profile binding/sync with profile management (photo upload, password change) through a nested ProfilesController. Consumes Application.Auth commands such as ChangePasswordCommand.

**Source File**: `src/CharityPlatform.Api/Controllers/Auth/AuthController.cs`

**Request Format**: application/json (Contracts.Auth DTOs) plus multipart/form-data for profile photo (IFormFile on BadRequest path when photo payload missing)

**Response Format**: application/json (ApiResponse envelope via overloaded HandleResult)

**Authentication**: JWT Bearer plus Supabase identity binding (identity profile synchronization); password change is credential-adjacent

### GET/POST/PUT/DELETE /api/v1/Cart

**Description**: Pre-donation funnel: accumulates campaigns into a cart and persists saved campaigns for both anonymous guests and authenticated donors. Bridges two identity models (guest + authenticated) into one dual-persistence design.

**Source File**: `src/CharityPlatform.Api/Controllers/Donations/CartController.cs`

**Request Format**: application/json (Contracts.Donations cart/saved-campaign DTOs)

**Response Format**: application/json (ApiResponse envelope via six HandleResult overloads)

**Authentication**: Mixed: anonymous guest support for cart operations; JWT Bearer for authenticated donor state

### GET/POST /api/v1/RecurringDonations

**Description**: Subscription-style giving surface: donors establish automated pledge schedules (weekly/monthly/yearly) rather than one-off contributions. Backed by a bounded context distinct from one-off donations (Application.Recurring + Contracts.Recurring).

**Source File**: `src/CharityPlatform.Api/Controllers/Donations/RecurringDonationsController.cs`

**Request Format**: application/json (Contracts.Recurring DTOs)

**Response Format**: application/json (ApiResponse envelope via HandleResult)

**Authentication**: JWT Bearer ([Authorize] attributes)

### GET/POST /api/v1/Reservations

**Description**: Scarce-inventory reservations for ritual offerings (Qurban/Aqiqah/Waqf shares). Atomic temporary capacity claims with a 15-minute TTL auto-release. Concurrency-sensitive; potential double-booking surface during peak seasonal demand.

**Source File**: `src/CharityPlatform.Api/Controllers/Donations/ReservationsController.cs`

**Request Format**: application/json (Contracts.Reservations reservation commands/queries)

**Response Format**: application/json (ApiResponse envelope via HandleResult)

**Authentication**: None declared at controller level (import set notably omits Microsoft.AspNetCore.Authorization) — anonymous access to capacity reservation endpoints

### GET /api/v1/Financial

**Description**: Money-related read operations: ledger audits, financial summaries, campaign balances, and net organization payouts. Governs ledger and payout visibility; routes into IQueryDispatcher/IQueryHandler and normalizes via eleven HandleResult overloads including PagedResult<T> and Error.

**Source File**: `src/CharityPlatform.Api/Controllers/Financial/FinancialController.cs`

**Request Format**: application/json / query string parameters (financial query DTOs in Contracts.Financial/Contracts.Campaigns)

**Response Format**: application/json (IActionResult with paged and non-paged ApiResponse envelopes)

**Authentication**: JWT Bearer ([ApiController] + [Authorize]) — critical authorization boundary for BOLA/IDOR and role-based access mistakes

### GET/POST/PUT/DELETE /api/v1/Users

**Description**: Administrative user administration surface: list/retrieve users, assign or revoke RBAC roles, drive profile lifecycle, and toggle account status (suspend/activate). Eight CQRS-backed actions; weakness here translates directly into privilege escalation risk.

**Response Format**: application/json (ApiResponse envelope via HandleResult)

## Integration Suggestions

### HTTP Client / REST API integration (Blazor WASM -> ASP.NET Core API)

Register a typed HttpClient against the backend API base URL in the Blazor WASM client, mirroring the existing ApiClient pattern. The base URL is resolved from the 'ApiBaseUrl' configuration key (falling back to http://localhost:5000/api/v1/), normalized with a trailing slash, and the client injects the bearer token used by the backend JWT bearer authentication scheme.

**Example Code**:

```
// Program.cs (WASM client)
var builder = WebAssemblyHostBuilder.CreateDefault(args);
var apiBaseUrl = builder.Configuration["ApiBaseUrl"] ?? "http://localhost:5000/api/v1/";
apiBaseUrl = apiBaseUrl.TrimEnd('/') + "/";
builder.Services.AddScoped(sp => new HttpClient
{
    BaseAddress = new Uri(apiBaseUrl),
    Timeout = TimeSpan.FromSeconds(30)
});
builder.Services.AddScoped<ApiClient>();
await builder.Build().RunAsync();
```

**Best Practices**:

- Always set ApiBaseUrl with a trailing slash — relative URI composition via HttpClient requires the base address to end in '/'.
- Register HttpClient as a scoped service with an explicit 30-second timeout to match the existing Program.cs registration.
- Inject the bearer token through SetAuthorizationToken rather than mutating DefaultRequestHeaders manually.
- Treat the API's ApiResponse envelope as opaque at the boundary; unwrap Result<T> payloads on the client instead of duplicating error-mapping logic.

### Internal service integration (Blazor Server -> REST API egress)

Consume AdminApiClient as the sole egress point from the Blazor Server admin console. It aggregates DTO contracts from seven namespaces and exposes typed async calls per domain. Because it is 2425 lines with high dependency density, treat any contract or endpoint change as a coordinated change across AdminWeb, Api, and Contracts.

**Example Code**:

```
// AdminWeb composition root
builder.Services.AddScoped<AdminApiClient>(sp =>
    new AdminApiClient(
        sp.GetRequiredService<IHttpClientFactory>().CreateClient("api"),
        sp.GetRequiredService<ILogger<AdminApiClient>>()));

// Usage
adminApiClient.SetUserContext(userId, email, roles, token);
var campaigns = await adminApiClient.GetCampaignsAsync(page: 1, size: 20);
```

**Best Practices**:

- Construct AdminApiClient via DI with HttpClient + ILogger<AdminApiClient> only; never instantiate it directly.
- Call SetUserContext(userId, email, roles, token) on every authenticated request path so downstream authorization policies have the identity context.
- Rely on BuildLocalMenuFallback when the remote navigation menu is unavailable, rather than surfacing an error to the operator.
- Freeze a single snapshot of the Contracts DTO family per release; a change on either side of the boundary is a breaking change to both.

### Reverse proxy / edge ingress

Terminate TLS at the nginx:alpine edge container and reverse-proxy to the API and frontends. This is the single ingress boundary for public traffic; the API container should never be bound to the host network directly. Use parameterized environment variables (${...}) for all secrets, and rely on depends_on ordering so the edge only starts after the backends are healthy.

**Example Code**:

```
# deploy/nginx/nginx.conf (excerpt)
upstream esalam_api { server api:8080; }
server {
  listen 443 ssl http2;
  server_name esalam.example;
  add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
  location /api/ { proxy_pass http://esalam_api; proxy_set_header Host $host; }
}
```

**Best Practices**:

- Terminate TLS at nginx and forward only to container-internal hostnames (api, public-web, admin-web) — never expose the API port directly to the public internet.
- Always validate the Host header at the edge; the API's [ApiController] layer does not itself enforce host allowlists.
- Keep health/readiness probes on a dedicated path so depends_on ordering and restart: unless-stopped policies can be enforced reliably.
- Pin the nginx configuration via a read-only bind mount (../nginx/nginx.conf) so config drift is impossible at runtime.

### Configuration / Secret injection

Drive the API container's runtime configuration entirely through shell-interpolated environment variables. The clearest map of the backend's external system dependencies: Postgres (Supabase pooler), Supabase URL/service key/JWT secret, and the ToyyibPay gateway secret. Every value is resolved from ${...} with no literal credentials in the compose file.

**Example Code**:

```
# .env (developer machine only; never committed)
DATABASE_CONNECTION_STRING=Host=...;Database=postgres;Username=...;Password=...
SUPABASE_SERVICE_KEY=eyJ...
SUPABASE_JWT_SECRET=...
TOYYIBPAY_SECRET_KEY=...

# deploy/compose/docker-compose.yml
environment:
  - ASPNETCORE_ENVIRONMENT=Production
  - ConnectionStrings__DefaultConnection=${DATABASE_CONNECTION_STRING}
  - Supabase__ServiceKey=${SUPABASE_SERVICE_KEY}
  - Supabase__JwtSecret=${SUPABASE_JWT_SECRET}
  - PaymentGateways__ToyyibPay__SecretKey=${TOYYIBPAY_SECRET_KEY}
```

**Best Practices**:

- Never commit literal secrets — the baseline compose already parameterizes everything through ${...}.
- Rotate Supabase__ServiceKey and payment gateway secret keys on a scheduled cadence and on any suspected compromise.
- Validate ASPNETCORE_ENVIRONMENT=Production to suppress developer error pages (which are a separate, higher-severity leak surface than the framework fingerprint).
- Fail fast at container start if any required ${...} variable resolves to an empty string, rather than letting the API boot with a broken connection.

### Observability / Telemetry pipeline

Instrument every esalam service to export OTLP telemetry to the OpenTelemetry Collector on gRPC 4317 or HTTP 4318. The collector applies batching and memory limiting, then fans out metrics to Prometheus (namespace 'esalam', exporter on 8889), spans to Tempo over OTLP/gRPC, and logs to Loki's push API. Prometheus then scrapes the collector exporter plus the api (8080), public-web (8081), and admin-web /metrics endpoints on a 5-second interval.

**Example Code**:

```
// Infrastructure/Telemetry registration (pattern)
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddOtlpExporter(o => o.Endpoint = new Uri("http://otel-collector:4317")))
    .WithMetrics(m => m
        .AddAspNetCoreInstrumentation()
        .AddOtlpExporter(o => o.Endpoint = new Uri("http://otel-collector:4318")));
```

**Best Practices**:

- Send all three signals (traces, metrics, logs) to the collector's single endpoint so backends never need to know the fan-out destinations.
- Keep the OTLP endpoint (4317/4318) on the internal network only — never publish the collector to the host.
- Name services with the 'CharityPlatform.Api' / 'CharityPlatform.PublicWeb' / 'CharityPlatform.AdminWeb' convention used by AddEsalamOpenTelemetry so dashboards group correctly.
- Treat the Prometheus exporter on 8889 as the only metric path out of the collector; do not scrape the API's /metrics from multiple Prometheus instances with conflicting interval settings.

### Payment gateway abstraction / Webhook boundary

Route all money-in operations through the pluggable IPaymentProvider adapters (StripeAdapter, ToyyibPayAdapter, ChipAdapter), resolved by a factory keyed on provider code. Keeping the boundary behind this interface de-risks vendor lock-in in the Malaysian market's fragmented payment rails and keeps webhook signature verification isolated per provider.

**Example Code**:

```
// Application layer
public interface IPaymentProvider
{
    string ProviderCode { get; }
    Task<PaymentInitiationResult> InitiateAsync(PaymentInitiationRequest request, CancellationToken ct);
    Task<PaymentCallbackResult> HandleCallbackAsync(PaymentCallbackRequest request, CancellationToken ct);
}

// Resolution
var provider = paymentGatewayFactory.Resolve(request.ProviderCode);
var result = await provider.InitiateAsync(request, ct);
```

**Best Practices**:

- Abstract every payment vendor behind IPaymentProvider; add new rails by implementing the interface plus a factory registration keyed on provider code.
- Verify inbound webhook signatures per provider (Stripe and ToyyibPay both sign) and reject unsigned callbacks before they reach the domain.
- Persist a payment_attempts record keyed by provider transaction id so duplicate webhook deliveries are idempotent.
- Never trust the amount in an inbound webhook payload — cross-check it against the pending payment attempt before mutating the ledger.
